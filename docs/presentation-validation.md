# 발표용 검증 방법과 사람 시간 측정

## 외부 연구로 설명할 수 있는 것

Google 연구 *Agentic Bug Reproduction for Effective Automated Program Repair at Google*은 버그 재현 테스트를 먼저 생성하는 접근을 평가했습니다. 자동 수정 비교에 선택된 **23개 버그**에서 Passerine의 plausible fix 수가 테스트 없이 **13개(57%)**, 생성 테스트를 제공했을 때 **17개(74%)**였습니다. 약 **17.4%p**, 수정 가능 사례 수 기준 약 **30.8% 상대 증가**입니다. 전체 연구의 80개 버그와 이 비교의 23개를 혼동하면 안 됩니다. plausible fix는 연구의 검증 기준을 충족한 수정 후보이며 모든 운영 상황에서 올바른 수정의 보장은 아닙니다. [논문 §6.2](https://arxiv.org/html/2502.01821v2)

발표 문장: “재현 테스트를 명확히 만드는 것은 후속 수정 검증에도 도움이 된다는 연구 근거가 있습니다. 우리는 그 앞단인 제보 해석·재현·증거 정리에 집중합니다.” 이 연구 결과를 우리 서비스의 정확도, 고객사 인건비 절감률, 자동 수정 성과로 옮겨 말하지 않습니다.

우리의 회귀 테스트도 같은 의미의 기준을 사용합니다. **동일한 테스트가 버그 버전에서 실패하고 수정 버전에서 통과하는지** 실제 실행합니다. 모델이 단순히 “재현 성공”이라고 말하는 것은 성공으로 세지 않습니다. 공개 개발용 사례에서 얻은 결과는 비공개 고객사 일반화 결과와 구분합니다. 작업에 맞는 평가·로그·사람 검토를 병행하라는 권고와도 맞습니다. [OpenAI 평가 권고](https://developers.openai.com/api/docs/guides/evaluation-best-practices)

## 엔진 성능 지표

| 지표 | 분자 / 분모와 판정 방식 |
|---|---|
| 사례 통과율 | 독립 채점 통과 작업 / 계획한 전체 작업. 오류·미완료를 임의로 삭제하지 않음 |
| 버그 재현 성공 | 실제 조작·완료·증상을 독립 확인한 작업 / 버그 작업 |
| 정상 오탐률 | 정상 화면을 재현 성공으로 판정한 작업 / 정상 작업 |
| 조건 비교 오탐률 | 정상 작업에서 **한 조건이라도** 버그로 판정한 부모 작업 / 정상 부모 작업 |
| 정상 조건 행 오탐률 | 잘못 양성 판정한 정상 행 / 정상 조건 행. 부모 오탐률과 함께 제시 |
| 보류·정보 부족 | 보류 사유와 필요한 정보가 기록됐는지, 실제 실행 불가를 음성으로 잘못 판정하지 않는지 |
| 수정 확인 | 같은 계획 해시로 버그 재현 후 수정 화면에서 정상 관찰 / 예정 버그 작업 |
| 테스트 다운로드 | 같은 생성 테스트의 버그 실패·수정 통과 쌍 / 검증 대상으로 정한 쌍 |
| 근거 완전성 | 판정·단계·필요 화면·실패 사유·요청한 영상의 실제 읽기 가능 여부. 영상 장애는 별도 표시 |
| 자동 소요 시간 | 준비·모델·브라우저·보고/영상 종료를 포함한 작업 시간의 중앙값·p95. 영상 옵션을 명시 |

사례 버전, 모델 ID, 프롬프트/코드 커밋, 실행 날짜, 반복 횟수, seed가 고정하는 대상, 호출/토큰 수, 누락/실패를 함께 남깁니다. 20개 사례를 3회 돌린 60작업은 서로 독립적인 60개 제품이 아닙니다. 표본이 작으므로 100% 통과도 “항상 성공”으로 표현하지 않습니다. 결과를 보고 프롬프트를 고쳤다면 개발 세트 성과라고 표시하고, 다음에는 미사용 고객 사례를 별도로 확보합니다.

## 현재 사람 시간 기준선

**아직 측정 기록이 없습니다. 시간·인건비 절감률은 미측정입니다.** 아래 절차와 빈 [CSV 양식](human-timing-template.csv)을 사용합니다. 예시 숫자를 관측치처럼 채우지 않습니다.

1. 실행 전에 사례 목록·시간 제한·완료 기준을 정합니다. 최소한 상태 전이, 버튼/레이아웃, 응답 오류, 정보 부족을 섞고 정상 사례도 포함합니다. 개발에 사용한 사례인지 표시합니다.
2. 수동 작업과 AI 보조 작업 모두 같은 제보와 승인된 환경 정보를 제공합니다. 완료 산출물은 “재현 여부, 정확한 단계, 기대/실제 결과, 근거, 막혔을 때 이유/추가 질문”으로 맞춥니다. 한쪽에만 정답이나 수정 상태를 알려주지 않습니다.
3. 가능한 여러 팀원이 참여합니다. 절반은 수동 먼저, 절반은 AI 보조 먼저 하도록 순서를 교차 배정합니다. 같은 사례를 다시 보면 학습 효과가 생기므로 순서와 참여자·사례 ID를 기록하고, 가능하면 충분한 간격/대응 사례와 교차 배정을 사용합니다. 소규모 편의 표본의 한계를 발표합니다.
4. 수동: 읽기·브라우저 재현·증거 수집·보고서 작성의 **사람이 실제 작업한 시간**과 시작~제출 **전체 경과 시간**을 각각 측정합니다.
5. AI 보조: 입력 준비·추가 질문 응답·결과 검토·오류 수정·재시도·최종 보고서 정리 시간을 모두 사람 시간에 포함합니다. AI를 기다리는 시간은 전체 경과 시간에 넣고, 사람이 그동안 다른 일을 했으면 사람 활동 시간에서 제외합니다.
6. 시간 초과/실패도 측정한 시간을 남기고 품질을 `false`로 기록합니다. 제외 이유를 사전에 정한 환경 장애 이외에 결과가 마음에 들지 않는다는 이유로 삭제하지 않습니다. 재실행 시 원 기록을 보존합니다.
7. 가능하면 방법을 모르는 다른 팀원이 동일한 완료 기준으로 품질을 판정합니다. 사실 오류, 잘못된 성공 판정, 실행 불가능한 단계, 근거 누락은 품질 실패입니다. 판단 불일치도 메모합니다.
8. 실제 시간당 비용과 해당 작업 API 비용을 확보한 경우에만 비용을 계산합니다. 비용이 없으면 빈칸입니다. 절감 시간이 실제 인원/급여 감소를 의미하지는 않습니다.

## 양식 작성과 집계

한 행은 같은 사례·참여자의 수동/AI 보조 작업 쌍입니다. `pair_id`는 고유값, `order`는 `manual_first` 또는 `assisted_first`, 품질은 `true/false`, 시간은 초입니다. `assisted_active_seconds`에 사람이 검토·수정한 시간을 반드시 합산합니다. `hourly_cost_usd`, `assisted_api_cost_usd`는 선택값이며 비교 통화는 USD입니다. 원화라면 별도 통일된 양식/환산 기준을 사용하고 섞지 않습니다.

```bash
PYTHONPATH=src python -m core_engine.evaluation.human_timing docs/human-timing-template.csv --output measured-timings.json
```

빈 양식의 결과는 `status=not_measured`, 절감률/비용 `null`입니다. 기록이 있으면 전체 시도 시간·품질 통과율·양쪽 품질 통과 쌍의 보조 지표를 함께 계산합니다. 비용이 하나라도 빠져 있으면 전체 순비용 절감을 산출하지 않습니다.

- 사람 시간 감소율 = `(수동 총 사람시간 - AI 보조 총 사람시간) / 수동 총 사람시간 × 100`
- 작업별 순비용 차이 = `사람시간 차이 / 3600 × 실제 시간당 비용 - 실제 API 비용`
- 전체 경과 시간과 사람 시간을 구분해 보고합니다. AI가 더 오래 걸려도 사람이 쓰는 시간은 줄 수 있고, 그 반대도 가능합니다.

발표 표기 예: “합성/실제 구분, 사례 N개·참여자 M명·작업 쌍 K개에서 관측. 검토·재작업 포함. 수동/AI 품질 통과 수를 함께 공개.” 숫자는 측정 후 채웁니다.
